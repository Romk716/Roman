## 3. Самый значимый дефект

Номер / ссылка: #19 (https://github.com/Romk716/Roman/issues/19)

## 5. Задание для закрепления

Выбран дефект #19: Потеря поля описания после перезапуска.

### 5.1. Почему этот дефект нельзя считать мелочью
Потеря данных - это не мелочь. Даже если потеряно только описание, пользователь теряет важную информацию, которую он ввёл. В реальном проекте это может привести к сбоям в бизнес-процессах, недовольству пользователей и необходимости восстанавливать данные вручную. Такие дефекты подрывают доверие к системе.

### 5.2. Что может пойти не так, если разработчик исправит его без ретеста
Если исправить только добавление поля в JSON, но не проверить, что другие поля (например, статус, дата создания) тоже сохраняются, можно случайно сломать их. Без ретеста не будет уверенности, что загрузка работает для всех полей и что не нарушена обратная совместимость с уже существующими файлами данных.

### 5.3. Какой один тест нужно добавить, чтобы дефект не повторился
Тест-кейс, который проверяет полное сохранение и восстановление всех полей задачи:
- Предусловия: файл tasks.json отсутствует.
- Шаги: создать задачу с названием, описанием, статусом (любым), приоритетом (если есть). Завершить программу. Запустить снова и вывести список.
- Ожидаемый результат: все поля задачи должны совпадать с исходными.
